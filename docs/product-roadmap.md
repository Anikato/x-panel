# X-Panel 产品路线图

> 状态：后续功能版本的主要推进方向
> 基线版本：X-Panel `v0.8.5`、定制 Agent `v2.4.0-xpanel.1`
> 更新日期：2026-10-30
> 适用仓库：`x-panel/`、`nezha/`、`admin-frontend/`、`agent/`

本文用于统一 X-Panel 后续功能版本的产品方向、组件边界、实施顺序和验收标准。它不是单个版本的详细技术设计；每个阶段开始前仍需补充独立设计文档、数据结构、接口契约、迁移方案和测试计划。

正式发布、Agent 绑定版本和生产部署继续以 [`../RELEASE.md`](../RELEASE.md) 为唯一操作依据。Dashboard、Agent 与 X-Panel 的职责边界以 [`dashboard-agent-xpanel.md`](dashboard-agent-xpanel.md) 为准。

## 1. 路线图目标

当前 X-Panel 已覆盖网站、证书、文件、终端、容器、数据库、计划任务、备份、HAProxy、Gost、主机管理和 Dashboard 集成。后续不再以堆叠孤立页面为主要目标，而是优先补齐以下运维闭环：

1. **发现问题**：集中看到节点、网站、证书、备份和任务风险。
2. **及时通知**：复用 Dashboard 通知组发送事件与恢复通知。
3. **安全恢复**：备份可校验、可预检、可恢复、可回滚。
4. **降低部署成本**：在现有 Compose 能力之上提供可信应用模板。
5. **持续加固**：以只读巡检为起点，逐步增加安全控制和身份治理。

## 2. 产品与架构原则

### 2.1 组件职责

| 组件 | 后续主要职责 | 明确不做 |
| --- | --- | --- |
| X-Panel | 本机业务管理、只读健康快照、备份恢复、安全巡检、应用模板执行 | 第二套中心控制面、Agent 协议客户端 |
| Dashboard | 多节点聚合、定时调度、风险展示、通知、版本与任务状态 | 直接覆盖 X-Panel 或 Agent 文件 |
| Agent | 采集节点状态、连接 Dashboard、执行受限远程任务 | X-Panel 业务逻辑、独立更新 X-Panel |
| 管理后台 | Dashboard 的集中运维界面 | 绕过 Dashboard 直接连接节点 |

### 2.2 长期约束

- Dashboard 保持唯一中心控制面，不恢复 Fleet Center、Fleet Reporter 或 Fleet v2。
- 优先复用 `xpanel invoke` 固定能力，不引入任意脚本式远程业务接口。
- 快照默认只读、最小输出、无敏感信息；不得返回密码、Token、私钥、证书私钥或完整环境变量。
- X-Panel 与 Agent 继续通过 X-Panel 正式包事务升级，不恢复 Agent 独立自动更新。
- 所有高风险写操作必须支持预检、审计、失败回滚和明确的最终状态。
- 新功能必须兼容 amd64、arm64，兼容旧配置，并对旧 Dashboard、旧 Agent、旧 X-Panel 给出明确降级行为。
- 未经明确授权，不执行生产批量变更；多节点功能默认先灰度、再扩散。

## 3. 版本推进方式

路线图按阶段推进。阶段编号表示依赖顺序，不强制绑定具体版本号；原则上每个主要阶段对应一个功能版本，阶段内修复使用补丁版本。

| 阶段 | 主题 | 主要仓库 | 建议顺序 |
| --- | --- | --- | --- |
| Phase 1 | 集中运维健康中心 | X-Panel、Dashboard、管理后台 | 最高 |
| Phase 2 | 备份恢复与灾难恢复 | X-Panel | 最高 |
| Phase 3 | 只读安全巡检中心 | X-Panel、Dashboard、管理后台 | 高 |
| Phase 4 | 轻量应用模板中心 | X-Panel | 中高 |
| Phase 5 | 网站安全增强 | X-Panel | 中 |
| Phase 6 | 通行密钥与多用户权限 | X-Panel | 条件触发 |
| Future | AI 安全管理接口 | Dashboard、X-Panel | 暂缓 |

Phase 1 与 Phase 2 构成第一条主线：先能发现问题，再能可靠恢复。Phase 3 与 Phase 4 构成第二条主线：降低巡检和应用部署成本。Phase 5、Phase 6 在核心闭环稳定后推进。

## 4. Phase 1：集中运维健康中心

> 实施状态（2026-10-30）：代码完成，待发布与生产灰度。已完成 `health.snapshot` 只读契约、X-Panel 本机采集、Dashboard 持久化与受限并发调度、细粒度状态、全局阈值与 5–60 分钟采集周期、事件历史、去重/静默/恢复通知，以及管理后台的筛选、详情、历史和静默操作。生产部署仍需按发布流程单独授权。

### 4.1 目标

在 Dashboard 中集中查看所有 X-Panel 节点的业务健康状态，并通过现有通知组发送异常与恢复通知。该阶段应复用当前 Agent 的受限命令执行能力，原则上不修改 Agent 协议。

### 4.2 X-Panel 交付物

新增只读能力 `health.snapshot`，通过 `/opt/xpanel/xpanel invoke` 固定入口调用：

```json
{"capability":"health.snapshot","payload":{}}
```

建议输出分区：

- `panel`：X-Panel 版本、启动时间、数据库可读状态。
- `services`：X-Panel、绑定 Agent、Nginx、Docker 等关键服务状态。
- `websites`：网站总数、禁用数量、健康检查失败数量。
- `certificates`：证书总数、即将过期数量、最近续签失败。
- `backups`：最近成功时间、最近失败时间、超过阈值未备份的对象。
- `cronjobs`：启用任务数、最近失败任务和连续失败次数。
- `storage`：关键挂载点使用率、Inode 使用率、备份临时目录可用空间。
- `security`：Phase 1 必需的基础风险，例如配置权限异常和服务漂移。

输出必须满足：

- 只读打开数据库，并启用 `PRAGMA query_only`。
- 设置总输出上限和每个列表的数量上限。
- 不返回日志全文，只返回截断后的错误摘要和时间。
- 不返回备份账户凭证、数据库密码、AgentSecret、SSH 密钥和证书内容。
- 对数据库忙、数据库不可读、能力不支持使用稳定错误码。

### 4.3 Dashboard 交付物

- 增加健康快照数据模型，按 `server_id` 保存最后成功结果、抓取时间、生成时间和状态。
- 增加后台调度器，默认每 10 分钟抓取一次，可配置为 5–60 分钟。
- 设置并发限制、单节点超时、指数退避和随机抖动，避免同时压满所有节点。
- 对离线、旧版不支持、超时、解析失败、数据过期分别分类。
- 快照数据设置保留周期，避免数据库无限增长。
- 风险事件支持去重、静默、恢复通知和最小通知间隔。
- 复用现有 Dashboard 通知组，不在 X-Panel 中再建设外部通知配置。

### 4.4 管理后台交付物

新增“X-Panel 运维总览”：

- 节点健康矩阵：正常、警告、严重、离线、不支持、数据过期。
- 风险卡片：证书、备份、计划任务、服务、磁盘、版本。
- 按节点分组、风险类型和严重等级筛选。
- 节点详情展示最近快照、风险变化和建议操作入口。
- 支持手动刷新单节点或选中节点，但不允许无限并发。
- 所有风险显示数据时间，避免把旧快照误认为实时状态。

### 4.5 默认风险规则

| 风险 | 默认等级 | 默认阈值 |
| --- | --- | --- |
| X-Panel 或绑定 Agent 未运行 | 严重 | 立即 |
| 备份连续失败 | 严重 | 2 次 |
| 重要对象长期无成功备份 | 严重 | 48 小时 |
| 证书即将过期 | 警告 | 15 天 |
| 证书即将过期 | 严重 | 7 天 |
| 计划任务连续失败 | 警告 | 2 次 |
| 磁盘使用率过高 | 警告 | 85% |
| 磁盘使用率过高 | 严重 | 95% |
| 健康快照过期 | 警告 | 3 个采集周期 |

所有阈值后续应允许在 Dashboard 中覆盖，第一版可先提供全局配置。

### 4.6 验收标准

- 旧 X-Panel 节点显示“不支持”，不会被标记为故障。
- Agent 离线、命令超时、数据库忙和输出过大都有独立状态。
- 快照中不存在敏感字段或 PEM 内容。
- 17 个节点同时启用时不会形成无界并发。
- 同一风险持续存在时不会重复刷屏；恢复后只发送一次恢复通知。
- Dashboard 重启后调度状态、历史记录和静默配置保持一致。
- X-Panel、Dashboard 和管理后台测试全部通过。

### 4.7 明确不做

- 不在该阶段增加远程修复按钮。
- 不允许 Dashboard 下发任意 Shell 作为健康检查。
- 不修改 Agent 自动更新策略。

## 5. Phase 2：备份恢复与灾难恢复

### 5.1 目标

把现有“能够生成和下载备份”提升为“能够证明备份可用，并安全恢复”。优先完成单机恢复闭环，再考虑 Dashboard 集中查看恢复状态。

### 5.2 Phase 2A：备份校验与恢复任务

新增能力：

- 对本地和远程备份重新计算 SHA256，并与记录值比较。
- 对加密备份验证密码和归档结构，但不写入目标目录。
- 解析归档清单，显示文件数、逻辑大小、压缩格式、加密状态和来源信息。
- 防止路径穿越、绝对路径、符号链接逃逸、设备文件和危险权限。
- 增加异步恢复任务模型，记录阶段、进度、日志摘要和最终状态。
- 允许取消尚未进入提交阶段的恢复任务。

恢复前必须执行：

1. 下载或定位备份文件。
2. 校验 SHA256。
3. 验证解密密码。
4. 检查磁盘空间和 Inode。
5. 检查目标路径、归档路径和权限风险。
6. 生成恢复计划并要求用户确认。

### 5.3 Phase 2B：网站和目录恢复

首批支持：

- **目录恢复**：恢复到原路径或新路径。
- **网站恢复**：恢复网站目录，并按备份元数据恢复可安全重建的站点配置。
- **数据库恢复**：复用现有数据库恢复能力，统一纳入恢复任务和审计记录。

提交恢复时必须：

- 自动创建恢复前快照。
- 优先解压到同文件系统临时目录，再原子切换。
- 对覆盖、合并和恢复到新路径提供明确模式。
- 网站配置变更先执行 `nginx -t`，失败则回滚。
- 保留原目录直到恢复通过健康检查。
- 记录恢复所用备份、操作者、目标、耗时和回滚结果。

### 5.4 Phase 2C：X-Panel 配置快照

在网站和目录恢复稳定后，再增加完整配置快照：

- X-Panel 数据库和必要配置。
- Nginx 站点配置与证书引用关系。
- 计划任务、备份账户元数据和通知偏好。
- 不直接导出明文敏感信息；敏感配置必须使用面板凭证密钥加密。
- 支持同版本恢复，跨版本恢复必须通过显式迁移流程。

完整配置快照不等同于整机镜像，不负责备份操作系统、容器镜像层或外部数据库全部数据。

### 5.5 前端交付物

- 备份记录增加“校验”“查看内容”“恢复”操作。
- 恢复向导显示来源、校验结果、目标、冲突、空间需求和风险。
- 恢复任务页面展示实时阶段、日志摘要、失败原因和回滚状态。
- 高风险覆盖操作需要二次确认，不能只依赖普通确认弹窗。

### 5.6 验收标准

- 被篡改、截断或密码错误的备份无法进入提交阶段。
- 恶意归档无法写出恢复临时目录。
- 恢复失败后原数据、原 Nginx 配置和服务状态保持可用。
- 恢复成功后执行网站、数据库或目录对应的健康检查。
- 本地、S3、SFTP、WebDAV 至少各完成一次端到端验证。
- 大文件恢复不把整个归档读入内存。
- 所有恢复操作都有不可歧义的审计记录。

### 5.7 明确不做

- 第一版不允许 Dashboard 批量远程恢复多个节点。
- 不提供“忽略校验继续恢复”。
- 不把恢复密码写入任务日志或数据库明文字段。

## 6. Phase 3：只读安全巡检中心

### 6.1 目标

建立可解释、可追踪的安全基线检查。第一版只报告风险和修复建议，不自动修改服务器。

### 6.2 检查范围

#### 主机与访问

- SSH 是否允许 root 密码登录。
- SSH 配置是否通过 `sshd -t`。
- 面板安全入口、HTTPS、MFA 和会话设置是否合理。
- 关键目录和敏感配置权限是否过宽。
- 系统是否存在待安装的安全更新。

#### 网络与服务

- 监听端口与防火墙规则是否存在明显偏差。
- Docker 发布端口是否绕过预期访问控制。
- 异常失败或长期重启的 systemd 服务。
- Nginx、Docker、数据库是否暴露到非预期地址。

#### 容器

- `privileged`、Host Network、Host PID、Docker Socket 挂载。
- 未固定镜像版本或使用 `latest`。
- 敏感环境变量和不安全卷挂载提示。

#### 数据与恢复

- 最近成功备份时间。
- 备份校验状态和异地副本状态。
- 证书过期和自动续签失败。
- 计划任务连续失败。

### 6.3 数据与界面

- X-Panel 保存巡检规则版本、结果、证据摘要和首次/最近发现时间。
- Dashboard 聚合节点得分和风险数量，不保存敏感证据原文。
- 风险必须包含检查说明、影响、证据摘要和手动修复建议。
- 支持忽略到指定日期，并记录忽略原因和操作者。
- 规则升级后区分“新增风险”和“已有风险重新评估”。

### 6.4 验收标准

- 巡检不得修改防火墙、SSH、软件包、容器或服务。
- 命令执行设置超时、输出上限和允许列表。
- Debian/Ubuntu 首先支持；其他发行版显示“不支持”，不能误报。
- 每个高风险规则至少包含阳性、阴性和不支持场景测试。
- Dashboard 的风险统计与节点详情一致。

### 6.5 后续自动修复原则

自动修复不属于 Phase 3 首版。未来增加时，每项修复必须单独满足：

- 展示变更预览。
- 创建配置备份。
- 执行语法或连通性验证。
- 保留当前管理连接。
- 失败自动回滚。

## 7. Phase 4：轻量应用模板中心

### 7.1 目标

复用现有 Docker Compose 管理能力，提供可信、可审计、可升级的应用模板。第一阶段不追求大型公共应用商店，而是先建立安全模板格式和少量高质量应用。

### 7.2 模板内容

每个模板至少包含：

- 应用元数据、版本、架构支持和来源链接。
- 固定镜像版本和镜像摘要策略。
- Compose 模板与参数表单定义。
- 端口、卷、环境变量和依赖说明。
- 健康检查。
- 安装、升级、备份和卸载注意事项。
- 数据目录和权限要求。

### 7.3 安全模型

- 模板仓库清单必须支持签名或固定可信公钥校验。
- 下载内容必须校验 SHA256。
- 默认不允许模板执行任意宿主机脚本。
- 必须执行端口冲突、目录冲突、架构和 Docker 版本预检。
- 安装前展示最终 Compose 和所有将创建的目录。
- 密码在本地生成并按敏感字段处理，不进入普通日志。
- 升级前自动生成应用数据备份或明确提示没有可用备份。

### 7.4 首批建议模板

首批控制在 5–10 个，优先选择维护稳定且有官方容器镜像的项目，例如：

- OpenList
- Uptime Kuma
- Vaultwarden
- Gitea 或 Forgejo
- MinIO
- PostgreSQL、Redis 等开发环境模板

实际收录前必须重新核对官方部署文档、镜像来源、许可证和架构支持。

### 7.5 生命周期与验收

- 安装：参数校验、目录创建、Compose 启动、健康检查。
- 更新：版本差异、备份、拉取、重建、健康检查、失败回滚。
- 卸载：区分删除容器、删除配置和删除数据。
- 迁移：导出模板参数和数据备份，但不导出明文密码。
- 模板被篡改时拒绝同步或安装。
- 不支持的架构不能安装。
- 安装失败不留下半创建记录和无主 Compose 项目。
- 每个首批模板完成全新安装、升级、备份恢复和卸载验证。

## 8. Phase 5：网站安全增强

### 8.1 目标

在现有 Basic Auth、证书、Nginx 配置测试和日志分析基础上，增加常用且可解释的网站访问控制。暂不直接建设完整 WAF。

### 8.2 功能范围

- 网站维护模式和自定义维护页面。
- IPv4、IPv6、CIDR 允许/拒绝规则。
- 仅允许 Cloudflare 回源，并可更新官方 IP 段。
- 常见机器人 User-Agent 拦截。
- 按站点配置请求速率和连接数限制。
- 安全响应头模板。
- 规则命中计数和最近命中摘要。

### 8.3 变更安全与验收

- 所有规则生成独立 include 文件，不直接拼接到不可控位置。
- 保存前生成预览并执行 `nginx -t`。
- Reload 失败时恢复旧配置。
- Cloudflare IP 段更新失败时保留旧版本。
- 白名单优先级和生效范围在界面明确展示。
- IPv4、IPv6、CIDR 和代理真实 IP 场景均有测试。
- 规则修改不覆盖用户自定义 Nginx 配置。
- 每次变更可追溯、可预览、可回滚。

首版不实现复杂 ModSecurity/OWASP CRS 规则管理，也不宣传为完整 WAF 或 DDoS 防护。

---

## 9. Phase 6：通行密钥与多用户权限

### 9.1 启动条件

当 X-Panel 明确需要多人协作、分权或对外提供托管能力时启动。个人单管理员场景下，该阶段优先级低于恢复、安全巡检和应用模板。

### 9.2 功能范围

- WebAuthn/Passkey 登录与恢复流程。
- 多用户管理和强制会话失效。
- 内置角色：管理员、运维、只读。
- 按节点、网站或功能模块授权。
- 操作日志记录实际用户、目标节点和权限来源。
- 高风险操作可要求重新验证 MFA 或 Passkey。

### 9.3 兼容与验收

- 现有管理员自动迁移为系统管理员，原 MFA 配置保持可用。
- 权限默认拒绝，旧单用户安装升级后行为不变。
- 跨节点代理请求不能绕过权限。
- WebSocket、文件下载和终端 Access Ticket 绑定用户会话与权限。
- 用户被禁用或会话撤销后，已有票据立即失效。
- 所有角色边界都有后端测试，不能只依赖前端隐藏按钮。

## 10. Future：AI 安全管理接口

该方向暂缓，不进入近期版本承诺。未来若恢复，应建立在 Phase 1–3 的只读快照、审计和恢复能力之上。

最低安全要求：

- 使用独立 API Token，不复用浏览器 JWT、管理员密码或 AgentSecret。
- Token 具有细粒度 scope、有效期、来源限制和随时撤销能力。
- 默认只读；写操作支持 dry-run、变更预览和人工确认。
- 高风险操作进入审批队列，不允许 AI 直接获得 root Shell。
- 所有请求、审批、执行和回滚写入不可歧义的审计记录。
- 多节点 AI 管理入口优先位于 Dashboard，避免新增中心控制通道。

## 11. 跨阶段公共基础设施

### 11.1 任务模型

恢复、模板安装、巡检和后续远程操作应尽量复用统一任务语义：

```text
pending -> validating -> running -> verifying -> success
                                      |-> rollback -> rolled_back
                                      |-> rollback -> rollback_failed
             |-> cancelled
             |-> failed
```

任务记录必须包含：类型、目标、创建者、开始/结束时间、当前阶段、进度、结果摘要和审计关联 ID。

### 11.2 敏感信息

- DTO 默认不输出敏感字段。
- 日志进入持久化前完成脱敏。
- 密码、Token、私钥只通过专用敏感写入路径处理。
- 密钥为空表示“保留原值”，不能被误解释为清空。
- 错误信息不得拼接完整命令行、请求头或远程响应中的凭证。

### 11.3 兼容性

- 新能力返回稳定的“不支持”状态，而不是把旧节点视为失败。
- 数据库迁移保持可重复执行，并为降级读取保留兼容字段。
- Dashboard 在 Agent 或 X-Panel 版本不足时隐藏不安全操作，但仍显示原因。
- 只有协议确实变化时才修改 Agent；如果 Agent 变化，必须先发布 Agent，再发布绑定它的 X-Panel 补丁版本。

### 11.4 可观测性

- 所有后台任务提供结构化阶段和耗时。
- 关键失败提供错误分类，不只保存自由文本。
- 监控调度器暴露成功率、延迟、超时和积压数量。
- UI 显示数据采集时间、来源和是否过期。

## 12. 发布与灰度策略

每个主要阶段至少经过：

1. 单元测试和前端测试。
2. 本地 amd64/arm64 构建验证。
3. 测试节点升级与回滚。
4. 单个生产节点灰度。
5. 观察服务、数据库、Agent 连接和 Dashboard 状态。
6. 小批量节点扩散。
7. 全量节点升级。

涉及恢复、模板升级或安全配置写入时，必须额外执行故障注入：磁盘满、权限错误、网络中断、进程被杀、服务启动失败和健康检查失败。

## 13. 阶段完成定义

一个阶段只有同时满足以下条件才可标记完成：

- 功能位于正确组件，不违反 Dashboard/Agent/X-Panel 边界。
- 数据模型、接口和错误码有文档。
- 敏感信息保护经过测试。
- 失败回滚路径经过真实验证。
- 后端、前端及相关跨仓库测试通过。
- amd64、arm64 构建通过。
- 升级旧版本后保留现有配置和定制功能。
- 用户文档、发布说明和运维说明同步更新。
- 正式发布通过 `Build & Release` 工作流完成，并验证公网包与 SHA256。

## 14. 近期执行建议

后续开发按以下顺序建立具体任务：

1. 为 Phase 1 编写 `health.snapshot` 数据契约和威胁模型。
2. 实现 X-Panel 只读健康快照及敏感字段测试。
3. 实现 Dashboard 定时抓取、持久化、过期判断和通知去重。
4. 实现管理后台运维总览。
5. 为 Phase 2 编写备份归档格式、恢复状态机和回滚设计。
6. 先交付备份校验，再交付目录恢复，最后交付网站和配置恢复。
7. Phase 1、Phase 2 稳定后启动只读安全巡检。
8. Compose 模板格式和签名方案评审通过后启动 Phase 4。

在以上主线完成前，不建议优先投入完整 WAF、虚拟机管理、大型公共应用商店或第二套多节点控制系统。
